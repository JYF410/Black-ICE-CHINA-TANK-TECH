## 一、问题

1. 科技树右侧的条纹底纹/暗色底板没有铺到窗口右边，1935~1942 年份数字离右边框约 200~400px；

## 二、当前结论（重要）

- 布局代码很可能是对的，**观测偏差来自科技树被平移/滚动**：
  用户 06:10 截图里最左边武器图标在 x≈390，而未平移时应在 x≈830，**平移量约 440px**。
  年份数字属于可滚动内容，会跟着一起左移，所以"永远差一段"。
- 另一个反复误导的因素：**`maxWidth = 10000` 不是定位手段**，只是文本框最大宽度。GER 的年份列之所以贴右边，是因为它锚在 3420 宽的条纹容器右端、且视野停在内容最右端。

### 2. `logs/system_debug.log` 的"越界控件"诊断（最有价值）

做法：**注释掉父容器的滚动条**，再加一个 `x = 9000` 的按钮；引擎就会把该控件判为越界并打印出来。06:01 实测输出：

```
Object "chi_probe_9000" has illegal position with x: 9000 and y: 9000
    in "trm_armour_chi_folder" with width: 4 and height: 4
Object "techtree_bg_full" has illegal position with x: 0
    in "trm_armour_chi_folder" with width: 2200
Object "techtree_stripes" has illegal position with x: 0 and y: 0
    in "trm_armour_chi_folder" with width: 2100 and height: 1820
Object "chi_year_col" has illegal position with x: 1840 and y: 50
    in "trm_armour_chi_folder" with width: 220 and height: 1820
Object "tech_trm_chi_armour_tree" has illegal position with x: 190 and y: 165
    in "trm_armour_chi_folder" with width: 2202 and height: 1484
```

可读出：①新文件确实被加载（`chi_year_col` 是新加的）；②`width/height` 是**控件自身**尺寸（不同控件数值不同）；③凡是 `x+width` 超过父容器宽度的都会被报，说明**文件夹宽度 < 2100**，与设定的 2060 吻合。

### 3. GER 的原始定义（`1851181613`，15287~15585 行）

```
containerWindowType = {
    name = "year_right"
    position = { x = 10 y = 0 }          ← 只偏 10px
    orientation = upper_left
    instantTextBoxType = {
        name = "year1"
        position = { x = 0 y = 280 }
        text = "1934"
        maxWidth = 10000                  ← 只是最大宽度
        maxHeight = 145
        format = left
    }
    ...
}
containerWindowType = {
    name = "year_left"                    ← 小号数字（maxWidth 80、height 32）
    position = { x = -90 y = 50 }
    orientation = upper_right
    ...
}
```

**命名反直觉**：GER 里大号年份列叫 `year_right`（但锚在左侧 x=10），小号列叫 `year_left`（却锚在右上角 -90）。照抄名字会搞反。

## 六、为什么会出现"连续 9 次无变化"

按可能性排序：

1. **科技树被平移**（`drag_scroll`，中键拖动，无边界钳制）。平移只移动内容、不动窗口右边框，所以无论我改多少坐标，用户看到的"离右边还差一段"都差不多；截图之间平移量不同，也无法互相比较。
2. **观测点被超宽文本框误导**：`maxWidth 10000` 的透明框横跨整行，`gui` 光标命中的永远是它，容易误判"这列数字属于哪个容器"。
3. 早期改的都是"背景/容器宽度"，本来就不会移动数字，用户自然感觉"完全没动"。

## 七、下次继续时的推荐步骤（按顺序，别跳）

1. **先消除平移变量**：把底部横向滚动条拖到最左端（或中键往右拖到底），确认最左列科技图标出现在 x≈830 附近（而不是 390）。
2. **确认文件已加载**：改一个无歧义的值（例如文本框 `maxWidth` 改成一个特殊数字），用 `gui` 控制台确认新值出现，再谈位置。
3. **确认目标容器**：用 `gui` 读到的名字 + 该容器是否有 `size`；没有 `size` 的容器布局不可控（这是 `year_left/year_right` 的老问题）。
4. **计算**：`屏幕 x = 文件夹起点(≈500) + 容器 x + 文本对齐偏移`。右侧贴边用 `x + width = 2060` 且 `format = right`。
5. 若仍不理想，改用**窗口层方案**：把年份列移到 `countrytechtreeview` 下、`orientation = upper_right`、`x = -100`，这样拖动科技树时它固定在窗口右边；代价是所有科技树文件夹都会显示，需要用 scripted GUI 控制显隐。

## 八、可复用的诊断手法

### A. 让引擎报告容器/控件尺寸

1. 临时注释父容器的 `verticalScrollbar` / `horizontalScrollbar`；
2. 在父容器里加一个越界控件：

```
buttonType = {
    name = "probe_x"
    position = { x = 9000 y = 9000 }
    quadTextureSprite = "GFX_tiled_window_transparent"
    size = { x = 4 y = 4 }
}
```

3. 启动游戏、打开该界面，读 `文档\Paradox Interactive\Hearts of Iron IV\logs\system_debug.log`；
4. 诊断完**务必还原**滚动条、删除探针。

### B. 确认游戏加载的是哪份文件

- 在 `.gui` 里加一个唯一名字的控件（如 `chi_probe_9000`），启动后看 `system_debug.log` 是否报它；
- 或用 `gui` 控制台读某个刚改过的数值（本次用 `maxWidth` 220 验证成功）。

### C. 像素对比的坑

- 截图必须是**未裁剪的整屏**；用户发的多为裁剪图（1209×822、1136×750 等），裁剪原点未知，无法换算像素。

## 九、踩过的坑（不要重复）

1. 把 `maxWidth = 10000` 当成定位参数 → 它只是最大宽度。
2. 在没确认"文件已加载"的前提下连续调坐标 → 浪费 9 轮。
3. 用 `orientation = upper_right` 但容器**没有声明 size** → 右对齐基准不可控。
4. 关掉用户正在用的 `drag_scroll` 做诊断 → 用户直接无法操作，必须先说明或事后立刻还原。
5. 一次改多个变量（背景 + 锚点 + 宽度）→ 无法归因。
6. 拿不同裁剪比例的截图互相比较位置 → 结论不可靠。

## 十、同期已解决、别再动的部分

以下问题在本轮之前已确认修好，改动不要回退：

1. **研发天数显示 0 / 不推进**：缺 `global.tech_cost` 与 `global.tech_date`。
   规则：`tech_cost = research_cost × 90`，`tech_date = start_year`。生成器 `_docs/gen_chi_research_arrays.py` 已内置（`COST_FACTOR = 90`）。
